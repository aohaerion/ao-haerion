# AO Haerion Principles

AO Haerion should grow through clear, readable, and restrained public development.

These principles guide the early documentation and milestone design.

## Clarity

The project should make complex work easier to understand.

Documentation should answer:

- what this is;
- what it does;
- what it does not do;
- what status it currently has.

## Traceability

Important statements should remain connected to their basis.

Decisions, evidence, assumptions, and limits should be kept separate where possible.

Traceability does not mean excessive bureaucracy.
It means that the path remains readable.

## Restraint

AO Haerion should not claim more than it can currently support.

A small clear milestone is better than a large vague promise.

## Human-readable structure

Public documentation should be understandable without requiring deep internal context.

Files should be:

- short enough to review;
- organized by purpose;
- written in plain technical language;
- useful to a reader arriving from GitHub or the public site.

## No overclaim

AO Haerion should avoid presenting drafts as validated systems.

The project should clearly distinguish:

- idea;
- draft;
- proposed milestone;
- implementation;
- validation;
- baseline.

## Progressive development

The project should grow step by step.

Each public layer should make the next one easier to understand.

Future milestones should be introduced only when the current milestone has a clear scope, non-goals, risks, and expected outputs.

## Haerion-first public layer

The public repository should stay focused on AO Haerion.

Broader systems, internal governance concepts, or future architectures should remain backstage unless they are ready to be explained clearly and safely in public.
